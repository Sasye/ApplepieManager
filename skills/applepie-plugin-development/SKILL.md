# Applepie 插件开发

把用户的功能需求实现为可构建、可诊断、能按约定停止和再次运行的插件。按实际功能选择接口与参考实现。

## 确定工程与 SDK

确定 `PLUGIN_ROOT`、含 `applepie.h` 的 `SDK_DIR` 与构建入口；涉及游戏访问时再确定目标游戏构建。优先使用用户提供的目录，再查工作区；skill 安装目录不是 SDK 目录。

先读当前 `SDK_DIR/README.md`、`applepie.h`。使用 C++ 时再读 `applepie_client.h` 和 `examples/minimal_plugin.cpp`；跨插件服务读 `examples/service_plugin.cpp`；基础设置和按键配置读 `examples/config_plugin.cpp` 与 Config 服务说明。SDK 缺失时先完成业务设计与纯数据部分，列出接入所缺文件，不编造接口。

管理器发布版本、SDK ABI、插件版本、服务契约版本分别管理。开发基线为 Manager v0.2.1 / ABI 1.1，具体以找到的头文件与运行宿主为准；Manifest 声明实际需要的 ABI。使用 `APH_PluginInfo` 或必需的新增服务时要求 ABI 1.1。

按任务选读以下参考，不必加载全部示例仓库：

- 涉及游戏方法、native Hook、托管对象、slot 或状态恢复：读 [游戏边界与 Hook](references/game-boundaries.md)。
- 需要 HUD、输入、基础设置、周期任务、姿态、MMD、网络或扩展服务：读 [功能模式与源码索引](references/plugin-patterns.md)中的对应部分。
- 任务是旧插件整体接入时，使用可用的 `applepie-plugin-migration`；本技能独立包含新开发所需的接入流程。

## 先确定功能的执行路径

用简短清单说明：触发条件、输入与可观察结果、必需与可选游戏接口、执行阶段/线程、持有资源、取消/恢复方式，以及最小验收动作。不要为此强制生成额外报告文件。

沿调用链分类，而非按功能名称分类：

| 实际操作 | 实现位置与接入方式 |
|---|---|
| 文件、配置、纯算法、自有网络/音频、独立 UI | 插件自行实现；自有任务参与取消和排空 |
| 简单设置与按键录入 | 可选 `applepie::Config` / `APH_ConfigApi`；Manager 提供原生控件及自动保存，业务应用由插件负责 |
| 解析地址或直接调用游戏方法 | 插件负责解析、准确原型、运行时及对象生命期；直接调用本身不需要 Hook 请求 |
| 普通入口 Hook | 模块期 `NativeHook<Tag, Function>`；特殊 ABI、提前筛选或错误状态要求用 `Hook` 加准确入口 |
| 观察其他插件也使用的入口 | 先查共享契约；匹配时用可选适配器，否则 `SharedHook` 与明确的新契约 |
| 指针槽替换 | 核对 Pointer 服务范围，再用 `APH_WithPointerPatch` 或显式 lease |
| 动画/相机共享状态写入 | 业务仍在插件内；按当前 Runtime/Write 契约申请及逐次进入写域 |
| 公共游戏窗口消息与命令 | Window 服务；独立窗口仍由插件管理 |
| 依赖另一个插件的业务能力 | 可选 `APH_PluginInfo` 依赖声明与 `APH_PluginServiceApi` |

GUI、网络和音频如果调用的是游戏内部服务，也需要对应运行时边界。只读观察参数不自动需要当前角色或写权；跨插件服务与消息队列也不自动授予游戏访问权。遇到缺少的写入域、Hook 类型或调度能力，具体说明并在任务范围内补足能力，不能套用无关写域或绕过 Core 安装补丁。

## 开发顺序

### 1. 找到最小可验证的功能入口

涉及游戏访问时，从目标效果倒推需要观察或改变的阶段，记录地址来源和完整原型。用当前元数据、导出、已有 dump 或反汇编互相核对；偏移和 RVA 必须关联游戏构建。未知签名先进行可控的只读定位，不能靠不同函数指针强转后反复尝试。纯插件工具从其文件、UI 或自有任务入口开始。

区分三种状态：插件 Active、依赖的游戏服务可用、业务目标/资源就绪。晚加载要能发现已经存在的对象、输入绑定或 UI，并继续跟踪后续变化；不能只等待下次创建事件。缺少可选接口时给出该功能的不可用原因，不让无关功能永远等待。

### 2. 将业务与游戏边界分开

解析、采样、插值、过滤、协议校验等采用可离线验证的普通 C/C++ 输入输出。游戏适配负责读取对象、转换数据和提交操作；UI/网络线程读快照、提交复制后的命令。

按职责组织代码，小插件可以从一个 `.cpp` 和构建脚本开始。只有独立复用、线程边界或编译依赖确有需要时才拆文件。新工程参考 SDK 最小示例调整 include 路径和插件 ID，不另维护一份公共 SDK 实现。

跨 DLL 使用固定 POD、SDK 句柄和约定回调，保持结构长度与 pack；C++ 容器和分配所有权留在各自模块内部。配置、姿态和校准文件应有版本与范围检查；保存时保留用户设置，诊断状态与持久配置分开。

### 3. 接入加载与生命周期

- 导出只读 DATA `APH_PluginManifest`、`APH_Attach`、`APH_Enable`。代理只引导 `plugin/applepie_manager.dll`，业务 DLL 由 Manager 扫描。DllMain/静态初始化保持被动。
- Attach 一次：保存 owner/API，按需获取并缓存服务表；支持异步启停时登记生命周期，建立模块期入口上下文。当前 `GAME/GUI` 为保留能力位，不能因使用游戏或绘图就声明为必需。
- 每次 Enable 使用新的 activation epoch。先准备必需入口与状态，再完成启用。异步初始化返回 Pending，由自有执行单元持有 epoch 副本，最终 `CompleteEnable`；等待支持取消及明确超时。
- 仅实际支持时声明 `LIFECYCLE`、`LATE_LOAD`、`MODULE_OBSERVER`；后两项要求同时声明 `LIFECYCLE`。常驻观察用于发现、停止、清理或纯配置通知，不延续已停用的业务。
- Enabling 期间也可请求逻辑停用；Pending 表示已受理，Busy 不等于取消完成。`disabling` 可与 Enable/初始化任务并发，只负责关准入、唤醒等待和取消任务。`restore` 确认在途任务退出、游戏状态恢复及引用释放后才返回 OK；需要游戏阶段时返回 Pending，由合法 checkpoint 推进。超时或恢复不确定时保留上下文并报错。
- Core 只计数受管调用；自有 worker、异步 I/O、定时任务的启动/关闭/计数必须有同步协议。关闭线程句柄或设置取消标志不能当作线程已经退出。
- 逻辑停用保留 DLL、native entry 和 original；普通停用不调用 `Retire()` 或 `FreeLibrary`。业务订阅按新 epoch 续订，旧订阅 Pending 时保留上下文直至排空。

同时区分业务状态与插件状态。例如停止播放、暂停、解冻、断开连接各有收尾语义；停止业务后仍可能保持插件 Active。重新运行不能被旧的 ready/once 标志或未完成的加载任务卡住。

### 4. 完成线程间数据流与状态恢复

命令保存复制的数据、serial、owner epoch，以及适用的目标/会话代次；执行前复验，结果也带相同身份。延迟的旧结果不能更新新一轮 UI 或覆盖新目标。队列有容量和满队列行为；游戏回调不等待 UI、磁盘、网络、Hook 激活或自己排空。

修改游戏共享状态时，先保存原值与可证明有效的对象身份，再做首次修改；恢复记录和实时计算缓存分别维护。释放写权前确认恢复完成。托管 root 只能维持托管存活，还需处理 Unity native 对象销毁、实例重建与场景/角色切换。详见[游戏边界与 Hook](references/game-boundaries.md)。

### 5. 按需接入基础设置

基础设置注册后显示在游戏设置的 **Applepie Manager → 插件 → 配置**。通过公开 Config 服务接入；Manager 的 Lua 页签和控件是宿主实现，业务插件继续使用 C/C++。插件的 HUD、自定义界面、复杂文件和联动逻辑按业务保留。

- 选择开关、整数、小数、枚举、短文本或按键类型。稳定 key 和枚举字符串用于持久化，数值范围及文本字节限制以当前 SDK 为准；字段和选项按实际数量分配。按键使用 `APH_CONFIG_KEY`，由 Manager 显示名称并录入，内部值是单个 Windows VK，0 为未绑定；响应、组合键和成对动作仍由插件实现。
- 在 Attach/初始化 worker 中注册一次模块期 `Config`，按 `Register → Notify → Read` 安装保存通知并读取初始快照。通知需要 `MODULE_OBSERVER` 与 `LIFECYCLE`，context 存活到进程退出；旧宿主缺少服务或可选通知扩展时明确处理能力缺失，不能假定 ABI 1.1 就包含它们。
- 通知在保存 worker 上串行执行，只读取快照并更新同步保护的缓存或发信号。业务直接读取本地缓存；不定时检查 revision、每帧读取快照或监听配置文件。逻辑停用时仍可更新纯配置数据，涉及游戏的应用和旧动作收尾留到合法业务阶段。
- 原生控件修改后自动保存，文字/数值在弹窗确认后保存。自定义配置 UI 通过 `Save(expected_revision, values)` 提交完整事务；成功落盘后新值才生效，Pending/Busy/Stale 和保存失败各自处理，禁止在游戏回调里等待或自动循环重试。

插件配置存放在 DLL 所在目录的 `config/applepie.<插件ID>.ini`，使用 UTF-8 扁平 `key=value` 和 `true/false`。让 Config 服务负责原子保存，不用另一套 writer 同时修改该文件；复杂业务文件单独维护。需要导入旧配置时，先确认新文件不存在，再校验旧值并注册为初始值，通过服务保存；新文件已有或损坏时不以旧文件覆盖，失败不宣称迁移成功。

`manager` 是保留配置 ID。Manager 自身配置为 `plugin/config/applepie.manager.ini`，默认模板位于完整 Manager 仓库的 `templates/config/applepie.manager.ini`；其 `plugin.<小写 DLL 文件名>` 仅是启动偏好。语言、UID 和统一启用开关由 Manager 管理，业务配置注册到自己的插件 ID。

### 6. 控制性能与诊断成本

根据入口频率选择采样率与缓存失效条件。先用廉价身份/参数筛选无关调用；必要 original 与 Core 计数仍配对。初始化缓存服务表与元数据；高频路径不重复申请 Hook、查询安装状态、遍历资源表或输出文件日志。缓存可保留地址和解析结果，不能永久缓存“允许写入”。

为明显高频的功能记录调用次数、反射/分配次数、单次与每帧总耗时；优化前后采用相同场景对照。HUD、文件载入、网络同步和逐帧姿态分别选择频率，不将某个插件的限频值变成统一标准。

错误携带功能阶段、`APH_Result` 名称、目标/资源及 owner epoch；按需通过 Diagnostics 上报。Pending、等待游戏对象和终止失败分开显示。Manager 的有界日志不自动轮换插件自建日志，自建日志也应限频及有界保存。

## 验证与交付

构建实际插件并核对导出、SDK include 路径和链接输入；普通业务插件不链接私有 MinHook。需要核对静态链接时使用 map/符号，不能只看 DLL imports。版本资源、Manifest ABI 和服务契约按各自版本核对。

按本次功能选择有价值的验证：

| 层级 | 核对内容 |
|---|---|
| 纯逻辑 | 真实解析/采样/状态机的边界数据、空数据及无效数据；适用时含坐标/时间/协议往返 |
| 独立宿主 | 实际插件启停；初始化取消和再次启用；参数/返回 ABI、original 次数、旧命令失效、恢复 Pending；涉及共享时覆盖两种加载顺序与 provider 停用 |
| 基础配置 | 初始值/重启持久化、按键录入和实际响应、通知更新缓存；保存失败保留旧值、旧 revision 被拒、停用时配置更新；涉及导入时验证新文件优先和损坏文件保留 |
| 手动游戏验收 | 冷启动与晚启用、主要功能、停止后再次操作、逻辑停用/启用；按功能增加切人、切场景、重绑、共存、退出及帧耗时比较 |

SDK 的 `examples/build.bat /verify` 与 `examples/verify_foundation.bat` 是框架基线，需完整 Manager 源码及后端，不能代替新插件的行为验证。仅改业务且不涉及公共契约时，选择相关检查，不机械重复整套框架测试。故障注入放在独立宿主。

交付源码、实际构建命令与产物路径、已验证结果、未确认的游戏行为，以及可执行的最小手测步骤。开发授权本身不包含部署、启动/注入游戏或提交/发布；已有明确授权按其范围执行。离线通过与游戏实测分别报告。
